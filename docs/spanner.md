# Google Cloud Spanner metadata

`scion-store-spanner` implements the `scion_store::Storage` metadata contract with the [official Google Cloud Rust SDK](https://github.com/googleapis/google-cloud-rust). It provides immutable records, transactional compare-and-swap, atomic changeset publication, and an ordered durable publication log. Immutable object bytes use a separate storage delegate. The authority combines Spanner metadata with the [cloud object adapter](cloud-storage.md).

This is this project's independently designed schema and implementation. Anthropic's [public Scion article](https://www.anthropic.com/research/redesigning-source-control) describes its use of Spanner but does not publish its table definitions, service implementation, or internal API.

## Provisioning

Create a **GoogleSQL** database in the appropriate Spanner instance. Apply [the four-table schema](../crates/scion-store-spanner/schema.sql) using an administrator or your infrastructure deployment system. The authority does not create databases or modify schemas on startup, so its normal identity does not need schema-administration permissions.

The schema stores:

| Table | Primary key | Purpose |
| --- | --- | --- |
| `ScionRecords` | namespace, record key | Immutable metadata, derived records, and mutable reference values |
| `ScionLogCounters` | repository | Last committed publication sequence |
| `ScionLog` | repository, sequence | Ordered changeset publication feed |
| `ScionPublished` | repository, changeset ID | Durable publication deduplication |

One database can host multiple repositories. Separate installations that need isolation should use separate databases. Cloud object prefixes must also identify the intended installation. Table names are fixed and versioned through the checked-in schema; this release has no automatic schema migration system.

Use [Application Default Credentials](https://docs.cloud.google.com/docs/authentication/application-default-credentials) or a platform identity recognized by the official SDK. For runtime access, assign the required [Spanner data permissions](https://docs.cloud.google.com/spanner/docs/iam) through IAM or a fine-grained database role. `--spanner-role` selects a database role; it does not grant that role. Supply bucket permissions independently for the object store. Credentials are not embedded in Scion metadata or configuration files generated by Scion.

## Start the authority

Build the server with `cargo build --release -p scion-server --features spanner`, or use the full release binaries. A GCS example is:

```sh
export SCION_CAPABILITY_KEY="$(openssl rand -hex 32)"
export SCION_SPANNER_DATABASE=projects/my-project/instances/scion/databases/scion
export SCION_CLOUD_PROVIDER=gcs
export SCION_CLOUD_BUCKET=my-scion-objects
export SCION_CLOUD_PREFIX=scion-production

scion-server \
  --listen 127.0.0.1:7420 \
  --policy policy.json \
  --spanner-database "$SCION_SPANNER_DATABASE" \
  --cloud-provider "$SCION_CLOUD_PROVIDER" \
  --cloud-bucket "$SCION_CLOUD_BUCKET" \
  --cloud-prefix "$SCION_CLOUD_PREFIX"
```

Use your service manager or secret manager to supply the capability key consistently across authority and cache services. The example generates a key for initial setup; regenerating it on each process start would invalidate existing capabilities. TLS termination, network exposure, authorization policy, and cache configuration follow [the operations guide](operations.md).

`--spanner-database` selects Spanner metadata and requires a cloud object backend. It conflicts with PostgreSQL metadata. The server does not require a local database directory in this configuration. S3 and Azure object storage are also supported: select their cloud provider and credentials independently.

| Option | Environment | Default |
| --- | --- | --- |
| `--spanner-database` | `SCION_SPANNER_DATABASE` | Required when selecting Spanner |
| `--spanner-role` | `SCION_SPANNER_ROLE` | SDK/IAM default |
| `--spanner-timeout-seconds` | — | 60 |
| `--spanner-max-inflight` | — | 64 |

The library constructor accepts `SpannerConfig` and a `SharedStore` object delegate. It can be used without the server or cloud crate. The supplied delegate is responsible for object durability in that composition.

## Transaction semantics

`put_record` reads and conditionally inserts the record in one read/write transaction. Identical writes are idempotent. A different existing value produces a conflict and rolls back. `compare_and_swap` reads the current value and performs its insert, update, or deletion in the same transaction. A failed comparison returns `false` without changing the value.

`publish_commit` validates the complete record batch before external writes. In one transaction it verifies existing immutable records, prepares missing records, establishes changeset membership, deduplicates the changeset ID, increments the repository counter, and appends its log entry. A conflicting record causes the entire transaction to roll back. Repeating publication returns its existing sequence. Publication leaves references unchanged.

The repository counter row is intentionally part of every new publication transaction. Spanner serializes conflicting updates to that row. This creates a committed sequence frontier: a reader that has observed sequence N will not later miss a lower sequence that commits after its cursor has advanced. Strong log reads and transactional publication depend on Spanner's [external consistency](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency).

This counter is a throughput coordination point within one repository. It does not meet a strict definition of lock-free durable publication, and this project does not claim the throughput or contention behavior of Anthropic's private deployment. Different repositories use different counters. Reference updates and unrelated immutable records use their own keys.

The official SDK retries aborted transactions. Scion wraps an entire operation, including those retries, in a configurable deadline and bounds outstanding operations. The synchronous `Storage` API submits I/O to a private Tokio runtime; the authority invokes it through its blocking worker pool. Dropping the backend from another async runtime does not synchronously destroy a nested runtime.

A timeout or broken connection during commit can leave the caller uncertain whether the remote commit completed. Immutable writes and publication can safely be repeated. After an uncertain compare-and-swap, read the current reference and decide whether the requested movement is already present before issuing a new expectation.

## Resource limits

The adapter enforces conservative limits below relevant [Spanner request, cell, and transaction quotas](https://docs.cloud.google.com/spanner/quotas):

| Resource | Adapter limit |
| --- | --- |
| Namespace | 1,024 UTF-8 bytes |
| Record key | 4,096 UTF-8 bytes |
| Repository name | 1–256 UTF-8 bytes |
| Metadata value | 8 MiB |
| Publication batch | 1,024 caller records; 32 MiB including keys and values |
| Metadata scan | 100,000 rows and 64 MiB of keys/values |
| Log read | 100,000 rows |
| Operation deadline | 1–300 seconds; 60 seconds by default |
| Concurrent operations | 1–1,024; 64 by default |

Limits are checked before cloning large caller batches. Large immutable file objects remain in object storage and use the object format's separate size bound. Scans use an explicit namespace, literal prefix matching, sorted keys, and a server-side limit; strings are bound parameters. Exceeding an aggregate result bound returns an error rather than a silently truncated result.

## Backup and recovery

Back up Spanner metadata together with the immutable object bucket. Restore metadata to a consistent snapshot and retain every object reachable from that snapshot. A bucket lifecycle policy must not delete objects still referenced by live or retained metadata. Spanner replication does not replace application backups, and the emulator is not persistent production storage.

The publication feed belongs to its database snapshot. Consumers restoring an older database should reset or reconcile their persisted cursors. Deduplication is scoped to repository and changeset ID. Do not clear counters independently of log and deduplication rows.

## Reproducible emulator tests

The workflow uses Google's official emulator, pinned to `1.5.59`. It runs actual gRPC transactions through the official Rust SDK. [The fixture script](../scripts/test-spanner.py) creates a temporary instance and database through the emulator's REST gateway, applies the checked-in schema, and runs the Rust contract test. It accepts only loopback emulator endpoints and removes the Google credential-file variable from its test subprocess.

With Docker:

```sh
docker run --rm -p 9010:9010 -p 9020:9020 \
  gcr.io/cloud-spanner-emulator/emulator:1.5.59
```

In another terminal:

```sh
python3 scripts/test-spanner.py
```

With Google's [standalone Linux emulator binaries](https://github.com/GoogleCloudPlatform/cloud-spanner-emulator#via-pre-built-linux-binaries):

```sh
python3 scripts/test-spanner.py --gateway /path/to/gateway_main
```

The standalone runner starts on ephemeral loopback ports, terminates both emulator processes on exit, and needs no Google account. Tests cover immutable idempotence/conflicts, concurrent compare-and-swap, deletion, UTF-8 prefix scans, atomic rollback after a prepared-record conflict, publication deduplication, cursor reads during concurrent publication, and reopening through a second client. Unit tests cover configuration and resource bounds.

The emulator validates API behavior and our transactional invariants. It does not establish production availability, WAN behavior, capacity, performance, IAM configuration, or backup recovery. Google's [emulator documentation](https://docs.cloud.google.com/spanner/docs/emulator) describes its differences from the service.

## SDK compatibility

The dependency is pinned to `google-cloud-spanner = 0.34.4-preview`, the official SDK release compatible with this workspace's Rust 1.88 minimum. The upstream SDK is a preview and may change its API. Upgrades require the emulator transaction contract, Rust minimum-version gate, package checks, and production deployment review. This project does not substitute the older similarly named community SDK.
